# ADR-008: Runtime events drive execution traces

## Status

Accepted

The default Console Trace presentation is refined by [ADR-018](018-console-traces-fold-inspection-tools.md); Runtime event ownership remains accepted.

## Date

2026-09-17

## Context

The Agent Loop printed each raw `ModelOutput` as JSON. That output omitted the beginning and end of a Turn, model request size, elapsed time, Tool execution state, Tool Result content, and serial versus parallel scheduling. It also coupled the reusable Runtime to one terminal presentation.

The OpenAI-compatible provider can return a non-standard `reasoning_content` field. Some models and responses omit it. A trace must distinguish provider-returned Reasoning Content from an explanation inferred or generated by the Runtime.

## Decision

`AgentSession` emits typed `AgentEvent` observations through one optional synchronous callback. Events describe Turn start and completion, Step start, model completion, Tool Call Batch scheduling, individual Tool start and completion, durations, content, and failures. The Runtime emits facts but owns no terminal formatting.

The CLI installs a Console Trace Adapter that renders the events as a readable timeline. It prints complete model Final Content and provider-returned Reasoning Content. The original presentation printed every Tool Result with a 4,000-character display limit; ADR-018 adds compact and verbose presentation modes. Storage and model feedback retain the complete value in either mode.

`ModelOutput.reasoningContent` is optional and is populated only when the provider response contains a non-empty `reasoning_content` string. A Tool Call response can also carry optional provider Content, which the trace displays instead of discarding. Reasoning absence is printed explicitly. Tool-call Content, Reasoning Content, and timing are transient observations in this version and are not projected into Messages or persisted as Session Records.

## Alternatives Considered

### Keep printing raw ModelOutput JSON

This exposes a provider adapter result but cannot show the execution lifecycle or Tool timing, and it mixes runtime diagnostics with the user interface.

### Put console logging directly around every operation

This is quick but makes the Runtime depend on terminal behavior and forces future JSON logs, a TUI, and tests to parse human-formatted text.

### Persist every trace event now

Durable traces would support post-run inspection, but adding a second event schema and database migration is premature before a trace query or export requirement exists. Existing Session Records remain the durable execution state.

## Consequences

- A CLI user can follow one Turn from input through every model inference and Tool execution to the final answer.
- Other user interfaces can observe the same Runtime interface without changing the Agent Loop.
- Provider Reasoning Content is visible when available but is never fabricated.
- Console rendering is testable independently from execution.
- A process crash still loses Reasoning Content. ADR-015 later made Model Invocation and Provider Attempt timing durable without persisting the reasoning text itself.
